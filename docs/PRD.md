# 即我「安排」模块 — 产品需求文档 (PRD)

## 1. 产品概述

### 1.1 产品定位

「即我」是一款面向个人的生活流记录与安排管理应用。与传统待办/日程工具不同，「安排」模块不做简单的任务列表，而是通过 AI 对用户的生活流信息（对话、自言自语等）进行智能分流，自动识别出真正值得用户后续执行的事项。

### 1.2 核心设计哲学

- **不制造焦虑**：安排项堆积不会用红色逾期提醒逼迫用户处理，过期事项温和归入"以后再说"
- **少打扰**：AI 识别结果默认为候选状态，需用户确认后才转为正式安排
- **人生充满变数**：不强制用户按预设轨迹执行，允许事项自然沉淀而非永远堆积

### 1.3 本次实现范围

本文档描述的是「即我」移动端前端 Demo 中已实现的安排模块功能，涵盖安排管理、消息测试后台及 AI 识别系统的完整闭环。

## 2. 功能模块

### 2.1 安排

**功能描述**：统一处理用户生活中"还没发生但需要后续执行落地"的事项，替代传统待办、日程、任务、提醒等分散模块。

#### 2.1.1 安排入口

安排模块不在底部导航栏中，而是从首页自然浮现——以胶囊按钮形式出现，点击进入安排中心。这种设计避免了"任务管理"的心理负担感。

#### 2.1.2 安排中心

安排中心分为两个主要区域：

| 区域 | 内容 | 操作 |
|------|------|------|
| AI 识别 | 候选安排（focus = confirm），带 AI 设置入口 | 查看详情 / 确认 / 忽略 |
| 正式安排 | 已确认的安排，带手动创建按钮 | 查看详情 / 完成 / 归档 |
| 归档（右上角入口） | 已完成 / 已归档的安排 | 查看历史 |

#### 2.1.3 安排生命周期

```
                    ┌── 忽略 ──▶ 归档
                    │
候选安排 (candidate)─┤
  (AI 识别待确认)    │
                    └── 用户确认 ──▶ 正式安排 (formal)
                                           │
                              ┌─────────────┼─────────────┐
                              ▼             ▼             ▼
                           完成           归档         放一边
                          (done)       (archived)     (quiet)
```

#### 2.1.4 关注度分层

安排项按关注度分为五级，决定其在首页的呈现方式：

| 关注度 | 含义 | 首页表现 |
|--------|------|----------|
| `today` | 今日关注 | 优先展示 |
| `recent` | 近期事项 | 常规展示 |
| `confirm` | 待确认 | AI 识别区展示 |
| `later` | 以后再说 | 归入归档 |
| `quiet` | 低打扰 | 归入归档 |

#### 2.1.5 执行方式

每条安排可标记执行方式，区分人工 / AI 边界：

| 类型 | 说明 | 示例 |
|------|------|------|
| `user` | 必须用户亲自完成 | 去医院检查身体 |
| `aiAssist` | AI 可协助部分，用户完成核心 | 整理资料（AI 先分类，用户确认） |
| `aiAuto` | AI 可全自动执行 | 发送定时提醒 |

#### 2.1.6 手动创建

用户可通过底部 Sheet 编辑器手动创建安排，支持填写：

- 标题（必填）
- 时间描述（"后天上午" / "明天上班前"）
- 地点
- 相关人（默认"我"）
- 备注
- 执行方式

#### 2.1.7 安排详情

详情页展示安排的完整上下文：

- 标题、时间、地点、相关人、执行方式
- 来源信息（哪个对话 / 谁说的 / 原文片段）
- 识别依据（AI 置信度、判断理由）
- 操作按钮：完成、归档、定位到原对话

#### 2.1.8 数据模型

```ts
type ArrangementItem = {
  uid: string;
  title: string;
  timeText: string;
  location: string;
  people: string[];
  note: string;
  status: "active" | "maybeDone" | "done" | "expired" | "archived";
  focus: "today" | "recent" | "confirm" | "later" | "quiet";
  source: {
    type: "manual" | "record" | "self" | "private" | "group" | "context";
    label: string;
    snippet?: string;
    recordUid?: string;
    conversation?: RecordSourceConversation;
  };
  confidence?: number;
  executionType: "user" | "aiAssist" | "aiAuto";
  createdAt: number;
  updatedAt: number;
};
```

### 2.2 消息测试后台

**功能描述**：独立于移动端 Demo 的测试控制台，用于模拟真实对话场景，验证消息接收和 AI 识别能力。

**访问地址**：`http://127.0.0.1:5173/sendtest`

**已实现能力**：

| 能力 | 说明 |
|------|------|
| 私聊模式 | 选择一个身份，向移动端 Demo 发送私聊消息 |
| 群聊模式 | 创建群组，以某身份在群组中发消息 |
| 身份管理 | 创建多个测试身份（姓名 + 备注） |
| 群组管理 | 创建群组，包含所有已创建的身份 |
| 消息列表 | 按时间排序的聊天气泡，区分自己/他人 |
| 跨标签同步 | 通过 StorageEvent 实现多标签页数据同步 |
| AI 自动识别 | 发送消息后自动触发 AI 分析，识别出的安排自动合并到安排列表 |

**交互流程**：

```
1. 创建测试身份（如"爸爸"、"姐姐"）
2. 选择私聊/群聊模式
3. 以某身份发送消息
4. 系统自动调用 analyzeLifeStream() 分析消息内容
5. 识别出的候选安排自动出现在移动端 Demo 的安排中心
```

### 2.3 AI 信息漏斗系统

**功能描述**：将原始生活流文本经过多层分析，分流为记忆、情绪、灵感、安排等不同类别，是安排模块的智能核心。

#### 2.3.1 漏斗流程

```
原始输入（对话 / 自言自语）
    │
    ▼
语义切片 ──── 按事件、情绪、承诺、想法拆成可判断片段
    │
    ▼
四向承接分流
    ├── 记忆 ──── 值得保存但不需执行的事实、偏好、关系
    ├── 情绪 ──── 焦虑、想念、压力、愤怒、释然等
    ├── 灵感 ──── 观点、洞察、创意、原则性判断
    └── 安排 ──── 未来动作、承诺、请求、准备、提醒
    │
    ▼
安排深度分析
    ├── 关系上下文 ──── 谁提出 / 谁承诺 / 谁执行 / 谁受影响
    ├── 事件聚合 ──── 同一生活事件的多个片段合并
    ├── 用户相关性 ──── 是否应进入当前用户安排
    ├── 未来性判断 ──── 是否尚未完成/闭合
    ├── 5W1H + Need ──── 结构化抽取，Need 是核心判断依据
    ├── 语气/安全 ──── 过滤玩笑、攻击、隐喻、高风险表达
    ├── 意愿强度 ──── "好的"/"我会" vs "可能"/"再说"
    └── Need 承接价值 ──── 是否值得系统承接
    │
    ▼
多来源合并 ──── 匹配已有安排，避免重复创建
    │
    ▼
结果路由
    ├── 候选安排 ──── AI 识别，待用户确认
    ├── 正式安排 ──── 手动创建或明确确认
    ├── 更新已有 ──── 补充来源 / 状态 / 完成证据
    ├── 放一边 ──── 暂不提醒，保留可回收价值
    └── 风险分流 ──── 攻击/隐喻/高风险，不生成安排
```

#### 2.3.2 输出结构 (FunnelResult)

漏斗的完整输出结构，所有字段必须存在，无内容时返回空数组：

```ts
type FunnelResult = {
  id: string;
  inputText: string;
  generatedAt: string;
  sourceRefs: FunnelSourceRef[];           // 输入来源
  memories: FunnelMemoryItem[];            // 记忆（事实/偏好/关系/事件上下文）
  emotions: FunnelEmotionItem[];           // 情绪（焦虑/想念/压力/愤怒/释然）
  inspirations: FunnelInspirationItem[];   // 灵感（洞察/创意/原则/问题）
  candidateArrangements: FunnelArrangementItem[];  // 候选安排
  formalArrangements: FunnelArrangementItem[];     // 正式安排
  mergeSuggestions: FunnelMergeSuggestion[];       // 合并建议
  arrangementGroups: FunnelArrangementGroup[];     // 安排组（展示层，非生命周期）
  ignoredItems: FunnelIgnoredItem[];       // 忽略项（可回收）
  riskItems: FunnelRiskItem[];             // 风险项
};
```

#### 2.3.3 运行模式

| 模式 | 说明 | 适用场景 |
|------|------|----------|
| mock | 规则匹配 + 预置样例，无需外部 API | 开发调试、Demo 展示 |
| openai | 调用 OpenAI 兼容接口，结构化 JSON 输出 | 接入真实 AI 能力 |

**mock 模式策略**（按优先级）：

1. 精确匹配 6 条验收样例（`funnelValidationCases.json`）
2. 精确匹配预置 fixture 样例（`funnelFixtures.ts`）
3. 关键词规则保守分流：
   - 风险信号 → 情绪 + 风险项（不生成安排）
   - 安排信号（明天/后天/提醒/准备…）→ 候选安排
   - 灵感信号（是/意味着/本质/洞察…）→ 灵感
   - 其他 → 忽略

**OpenAI 模式**：

- 使用 `response_format.json_schema` 约束输出结构
- System prompt 定义漏斗分流规则
- 输出经 `validateFunnelResult()` 严格校验
- 超时 20 秒，失败回退到空结果
- 用户可在安排中心自行配置 API Key、BaseUrl、Model

#### 2.3.4 多来源合并示例

```
输入来源：
  用户："后天去趟医院"
  父亲："一定记得去医院，知道吗？"
  用户："好的，我已经有安排了"
  姐姐："你这个身体情况怎么办？"
  用户："我已经到医院挂号了"

合并结果：
  → 一个「去医院检查身体」安排
  → 详情中保留全部 5 条来源上下文
  → "已经挂号了"作为进展证据，可更新安排状态
```

## 3. 技术实现

### 3.1 技术栈

| 层级 | 技术 | 版本 |
|------|------|------|
| 框架 | React | 18.3 |
| 语言 | TypeScript | 5.5 |
| 构建 | Vite | 5.3 |
| 样式 | Tailwind CSS | 3.4 |
| 包管理 | pnpm | 9.12+ |

### 3.2 数据持久化

所有数据存储在浏览器 localStorage 中，包括：

- 安排列表（`arkme-demo.arrangements`）
- AI 识别记录（`arkme-demo.aiRecognitionResults`，最多 30 条）
- 测试对话（消息、身份、群组、已读状态）
- 用户偏好（主题、语言、强调色）

### 3.3 跨标签页同步

消息测试后台和移动端 Demo 运行在不同标签页，通过 `StorageEvent` 和自定义事件实现数据实时同步。

### 3.4 AI 调用链路

```
消息发送 → analyzeLifeStream()
              │
              ├── mock 模式 → runMockArrangementFunnel()
              │                  ├── 查验收样例
              │                  ├── 查 fixture 样例
              │                  └── 关键词规则兜底
              │
              └── openai 模式 → fetch /chat/completions
                                 ├── system: funnelSystemPrompt
                                 ├── user: buildFunnelUserPrompt()
                                 └── response_format: json_schema
                                      │
                                      ▼
                                 validateFunnelResult()
                                      │
                                      ▼
                                 mergeAiRecognitionResultIntoArrangements()
```

## 4. 典型用户场景

### 场景一：自动识别安排

```
用户在消息测试后台以"爸爸"身份发送："一定记得去医院，知道吗？"
  → AI 漏斗识别到安排信号
  → 生成候选安排："去医院检查身体"
  → 移动端 Demo 安排中心出现该候选安排
  → 用户点击"安排"确认，转为正式安排
```

### 场景二：私聊承诺自动入安排

```
对方发送："明天来公司帮我带个早餐"
用户回复："好的"
  → 系统识别到承诺关系
  → 自动创建安排："明天到公司帮对方带早餐"
  → 关注度设为 today，执行方式为 user
```

### 场景三：手动创建隐喻事项

```
用户想安排游泳，但只记了"～～"
  → AI 无法识别隐喻含义
  → 用户手动创建安排，填写标题"游泳"、时间"周末"
```

### 场景四：多来源合并

```
用户说"后天去医院" → 创建候选安排
父亲说"记得去医院" → 来源合并到同一安排
姐姐问"身体怎样"  → 来源合并到同一安排
用户说"已经挂号了" → 更新安排状态，补充进展
  → 最终只有一个"去医院检查身体"安排，详情含全部来源
```
